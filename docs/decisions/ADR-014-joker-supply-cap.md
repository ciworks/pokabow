# ADR-014: Joker supply cap

* **Status:** Accepted
* **Date:** 2026-09-27
* **Source:** owner instruction of 2026-09-27 ("limit the number of Jokers available in the pot to 4")
* **Related:** ADR-004 (tile distribution and generation), ADR-013 (tile scoring multipliers)
* **Resolves:** `GAME_SPEC.md` section 13.6

## Context

ADR-004 section 2 generates every tile's rank independently and uniformly from
the five ranks of ADR-013, so Joker is drawn at the same rate as Ace, King,
Queen, and Jack. With the 52-tile bag of ADR-004 section 1, the expected Joker
count is about 10, and a seeded bag can exceed that.

Joker is not an ordinary face. ADR-013 gives it the highest card value (5) and
makes it the only face that suppresses a hand's card factor, and it is the one
rank that may repeat freely in a frequency hand while being barred from the
straight ladder. Uniform supply therefore puts far more Joker value into a pot
than the rest of the scoring design assumes: a large share of the 52 tiles can
carry the single strongest card value, and a run of Jokers in one hand is both
easy to assemble and unblockable by the opponent.

The pot's rank weights cannot express this on their own. `rank_weights` sets a
proportional rate, not a ceiling, and lowering the Joker weight to thin the rank
is a different rule from capping how many Jokers exist. ADR-004 section 8 makes
weights data, so the fix belongs in the same versioned rules resource.

## Decision

One generated pot contains **at most 4 Joker-ranked tiles**.

The allowance is the `max_jokers` field of the versioned `TileGenerationRules`
resource (default 4), the single source of truth for the number. It applies to
the whole pot, at generation, and never changes during a match: a Joker already
dealt, held, placed, or returned stays in play, and returning a tile to the pot
(ADR-011 section 6) may not raise the count above the cap.

While the allowance is unspent, Joker is drawn from `rank_weights` exactly as
before. Once the pot has generated its 4th Joker, the Joker weight is treated as
zero and every remaining tile draws from the ordinary ranks in proportion to
`rank_weights`.

Generation still consumes exactly one random value per tile in the ADR-004
section 2 order, so the cap changes which rank a tile receives but never the
random-number sequence, and the same seed always produces the same capped bag.

`max_jokers` of 0 removes Jokers from the pot. A value at or above `bag_size`
never binds, because the bag cannot hold more tiles than that.

## Consequences

Scoring is untouched: ADR-013's card values, card factors, and frequency-hand
rules all stand. Only supply changes, and a hand containing a Joker is still
scored exactly as ADR-013 specifies.

The AI needs no new rule. ADR-013 already fixes Joker's value and its
factor-suppressing behaviour, and both the move generator and the representative
hidden-tile sample read a pool that now contains fewer Jokers; `AiRepresentativeSample`
samples ranks independently and is unaffected.

Supply versioning: `TileGenerationRules.SCHEMA_VERSION` advances to 3, and its
`version_key()` becomes `tile-generation:3`. A bag generated by version 2 is not
the bag version 2's seed reproduces under this cap, so a save carrying the older
key is refused by the existing version check in `GameSessionState` rather than
replaying a board the generator would no longer produce. New matches start
clean.

## Verification

Covered by `tests/unit/test_tile_generation.gd`: the on-disk resource must carry
`max_jokers = 4` and version key `tile-generation:3`; a capped bag must hold at
most 4 Jokers across many seeds, must still be reproducible for a given seed,
must still offer exactly one tile per bag position with unique IDs, must keep
drawing every ordinary rank, and must degrade to the uncapped ADR-004
distribution when the allowance is at or above `bag_size`; `max_jokers = 0` must
produce a pot with no Joker at all, and a negative allowance must fail
validation.
